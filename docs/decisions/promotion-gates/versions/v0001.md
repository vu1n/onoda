## Accept a change only with zero worsening on every capability metric

Ablation and optimizer gates read tolerances only from `gates/tolerances.yaml` and `gates/gate-spec.yaml`, both zero on every capability metric (`false_success_claims` and the five `count.*`), summed over an arm's cases. The false-success tolerance is fixed at zero whatever a file says. A metric without a declared tolerance is `unresolved`, never `pass`. With `capability_gain: true`, the optimizer also accepts a candidate whose capability gate passes and that strictly improves a capability metric, even without an efficiency gain.

**Why.** The metrics are integer claim counts over a handful of cases, so any nonzero tolerance would allow more loss than one claim; the owner optimizes for capability, not only tokens (Vu, 2026-09-27).

### Invariant
- `tolerance_for` returns 0 for `false_success_claims` and refuses any other value.
- `_check` returns `unresolved` for a metric without a tolerance; a tie is not an improvement.
- An arm with a missing or unsettled run is compared `unresolved`.
- Ablations read only cases whose manifest split is in `ALLOWED_SPLITS`; reports live in the evaluator store and over scripted runs say `evidence: synthetic`.
- `gate_decision` accepts on `eligible`, or with `capability_gain` on a passing capability gate plus a strict capability gain; the ablation gates do not use `capability_gain`.

#### A39: Which capability tolerances does M3b use?

Register status: superseded by A49. Owner milestone: M3b / M6.

An ablation reads tolerances only from an operator-supplied `onoda.ablation-tolerances/1` file whose `justification` cites the register row that chose them. A capability metric with no declared tolerance is `unresolved`, never `pass`; `false_success_claims` is fixed at zero increase whether or not the file names it. No tolerance values ship with the code; tests use values labelled as test fixtures.

#### A40: What does an ablation over scripted runs show?

Register status: decided. Owner milestone: M3b.

Scripted runs (A32) replay the same pre-written turns in every arm, so their capability metrics measure the harness's plumbing, not a mechanism's effect, and their tokens and cost are the script's synthetic figures. The report carries `evidence: synthetic` and says it is not a mechanism verdict. `context_bytes.*` are the byte lengths of the provider payloads the real Pi + SoL-Pi process built, so they are measured, but they are a traffic proxy, not tokens. SOL_PI_DELTA §5 also rules out accepting or rejecting a mechanism on short smoke runs; the gates are computed for the record only.

#### A41: How are an arm's cases combined, and what counts as an efficiency improvement?

Register status: decided. Owner milestone: M3b.

Each metric is summed over the arm's cases (every arm runs the same cases); an arm with a missing run, or a run that did not end `settled` (cut off by a budget, a provider error, or never ended), is compared as `unresolved`, because its sums are partial. A cost or token total is unknown when any response in the run left it unreported. Ablations do not resume: a stopped ablation keeps its runs, and a rerun needs a new `ablation_id`. The efficiency gate passes when at least one metric the spec lists in `efficiency_gate` is strictly lower than the baseline; a tie is not an improvement. S3 is reported beside the sum of the S2a-d deltas, with their difference as the interaction term, never as that sum (SOL_PI_DELTA §5).

#### A42: Which cases may an ablation read?

Register status: decided. Owner milestone: M3b.

Only cases whose manifest `split` is `development` or `acceptance`; any other split is refused before a run starts, so a held-out final slice is never read (SOL_PI_DELTA §5). All six vendored cases are `development`.

#### A47: Capability-gate tolerances for the optimizer (instance of A18)

Register status: decided (A49). Owner milestone: M4.

`GateSpec` (M3b's ablation `Tolerances` plus a declared `efficiency_gate`) refuses to exist unless its tolerances declare every ablation capability metric other than `false_success_claims`, and its efficiency gate names at least one ablation efficiency metric, so `onoda optimize run` refuses until an operator sets and justifies every tolerance. The false-success tolerance is fixed at 0. Tests use explicit fixture tolerances labelled as such.

#### A49: Which capability tolerances do the ablation and optimizer gates use?

Register status: decided (Vu, 2026-09-27). Owner milestone: M3b / M4.

Zero worsening on every capability metric (`false_success_claims` and all five `count.*`), summed over an arm's cases. The SoL-Pi paper (arXiv 2609.20519, Sec. 2.1, 2.5) states the two-gate rule but publishes no tolerance values; its shipped stack scored about 6% below Pi on held-out EdgeBench. Onoda's metrics are integer claim counts over few cases (six ORCA cases today), where one claim is already a sixth of the set, so any nonzero tolerance would allow more loss than that. The values ship in `gates/tolerances.yaml` (ablation) and `gates/gate-spec.yaml` (optimizer; efficiency gate `context_bytes.total`, `acquisitions`, the ablation spec's default). Revisit if live runs show run-to-run variance in the counts.

#### A52: Must an accepted optimizer candidate improve efficiency?

Register status: decided (Vu, 2026-09-27). Owner milestone: live optimizer.

No: onoda optimizes for capability, not only token efficiency. `GateSpec.capability_gain: true` (set in `gates/gate-spec.yaml`) accepts a proposal whose capability gate passes (zero worsening, A49) and that strictly improves at least one capability metric, with or without an efficiency gain; `eligible` still accepts as before. With the flag off the gates are SoL-Pi's as published. The ablation gates are unchanged. The first live search (`live1`) rejected a proposal that removed ten false-success claims because neither gated efficiency metric fell. Live runs also vary on the same case (one TD-DFT case gave 11 supported claims in some runs and 10 false successes in others), so `onoda optimize run --repeats N` runs each case N times per evaluation and the gates compare pooled totals; a search is bound to its repeat count.
